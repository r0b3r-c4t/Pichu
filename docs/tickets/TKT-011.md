# TKT-011 — Gestión de vehículos (CRUD lógico multi-vehículo)

## 1. Propósito y alcance

TKT-011 expone la gestión completa de vehículos sobre la base de TKT-010: alta, listado paginado,
detalle, actualización parcial y archivado lógico. No introduce colecciones, índices, migraciones
ni dependencias nuevas, y no modifica Identity, Device ni Automation.

Fuera de alcance: transferencia de propiedad, administración de membresías, nuevas invitaciones,
AccessGrant público, `VehicleProfile`, catálogos, VIN, capacidades dinámicas, firmware, BLE y
frontend.

## 2. Endpoints

| Público (Gateway)                 | Interno (Vehicle)             | Política HMAC v2 | Éxito |
| --------------------------------- | ----------------------------- | ---------------- | ----- |
| `POST /api/vehicles`              | `POST /vehicles`              | `vehicleCreate`  | 201   |
| `GET /api/vehicles`               | `GET /vehicles`               | `vehicleList`    | 200   |
| `GET /api/vehicles/:vehicleId`    | `GET /vehicles/:vehicleId`    | `vehicleGet`     | 200   |
| `PATCH /api/vehicles/:vehicleId`  | `PATCH /vehicles/:vehicleId`  | `vehicleUpdate`  | 200   |
| `DELETE /api/vehicles/:vehicleId` | `DELETE /vehicles/:vehicleId` | `vehicleArchive` | 200   |

- El Gateway exige JWT y correo verificado en `/api/vehicles*`, deriva `userId` exclusivamente del
  JWT y lo firma dentro del cuerpo HMAC v2. Cualquier `userId`, `ownerUserId`, `status`, rol o campo
  interno enviado por el cliente se rechaza con 400 (esquemas estrictos).
- Vehicle verifica firma, nonce, deadline y HTTPS antes de parsear el cuerpo y consulta Identity
  (`/internal/users/:userId/verified`), que rechaza con 403 si el `userId` firmado no coincide con
  el sujeto del JWT reenviado.
- Las mutaciones (POST, PATCH, DELETE) se envían una sola vez; solo los GET admiten un reintento.
- Las peticiones firmadas con cuerpo que emite el Gateway (POST, PATCH y DELETE hacia Vehicle o
  Device) declaran `content-length` con la longitud en bytes UTF-8 de los mismos bytes firmados:
  el cliente HTTP de Node no enmarca por defecto los cuerpos de `DELETE`. Las peticiones GET no
  llevan cuerpo, `content-type` ni `content-length`. El encabezado no forma parte de la
  canonicalización HMAC v2.
- CORS permite `GET,POST,PATCH,DELETE,OPTIONS`. Swagger del Gateway y de Vehicle documenta los cinco
  endpoints con sus respuestas 400/401/403/404/409/5xx.

## 3. Contratos (`@pichu/contracts`)

### 3.1. Campos de vehículo

| Campo          | Tipo                      | Obligatorio | Límite |
| -------------- | ------------------------- | ----------- | ------ |
| `name`         | texto                     | sí          | 120    |
| `make`         | texto \| null             | no          | 80     |
| `model`        | texto \| null             | no          | 80     |
| `generation`   | texto \| null             | no          | 60     |
| `trim`         | texto \| null             | no          | 80     |
| `year`         | entero 1886..2100 \| null | no          | —      |
| `bodyStyle`    | texto \| null             | no          | 60     |
| `engine`       | texto \| null             | no          | 80     |
| `transmission` | texto \| null             | no          | 60     |
| `fuelType`     | texto \| null             | no          | 60     |

Normalización de texto, en este orden: rechazo de caracteres de control sobre el valor crudo,
`trim`, rechazo de vacío y validación de longitud. Vehicle repite la misma normalización en el
dominio (`normalizeVehicleFields`) con lista cerrada de campos.

### 3.2. Evolución del contrato

- `vehicleSummarySchema` pasa a los diez campos descriptivos más `id` y `ownerUserId`, sin `role`.
- `vehicleAccessViewSchema` (listado y detalle) añade `role` obligatorio (`OWNER` | `MEMBER`).
- `vehicleOwnerViewSchema` (respuestas de creación y actualización) fija `role: 'OWNER'`.
- `vehicleListResponseSchema` añade `page: { nextCursor: string | null }` obligatorio.
- Nuevos: `vehicleUpdateRequestSchema`, `vehicleArchiveRequestSchema`, sus variantes internas con
  `userId`, `vehicleUpdateResponseSchema`, `vehicleArchiveResponseSchema` y
  `vehicleListQuerySchema` (`limit`, `cursor`, `role`).

Es un cambio incompatible para consumidores que esperaban la forma anterior del listado o del
detalle (sin `role` ni `page`). Los consumidores del repositorio se actualizaron en este ticket.

## 4. Autorización

### 4.1. Lectura (listado y detalle)

Una única semántica, compartida con `evaluateVehiclePermission` mediante
`decideMembershipPermission` y `activeAccessGrantCriteria`:

1. El vehículo debe estar `ACTIVE` y su propiedad canónica debe ser consistente
   (`Vehicle.ownerUserId` ↔ única `Membership OWNER ACTIVE`). Cualquier inconsistencia produce
   NOT_FOUND y una auditoría en log, sin exponer el motivo.
2. El propietario canónico siempre lee.
3. Un MEMBER lee si su membresía vigente (`ACTIVE`, sin suspensión ni revocación) contiene
   `vehicle:read` o `vehicle:manage`.
4. En otro caso, solo un `AccessGrant` `ACTIVE`, de scope `VEHICLE`, canal `ONLINE` o `ANY`,
   dentro de su ventana `startsAt`/`expiresAt` y vinculado a la membresía, usuario y vehículo
   vigentes concede lectura. Los grants `DEVICE`, `MODULE` o `BLE_OFFLINE` no conceden lectura.

### 4.2. Mutaciones (PATCH y DELETE)

Exclusivas del propietario canónico, aunque un MEMBER tenga `vehicle:update` o `vehicle:manage`
por membresía o por grant. La relación actor–vehículo se resuelve sin escrituras y se traduce de
forma centralizada (`denyOwnerMutation`):

| Relación                                     | PATCH | DELETE                          |
| -------------------------------------------- | ----- | ------------------------------- |
| Propietario, vehículo `ACTIVE`               | 200   | 200 (archiva)                   |
| Propietario, vehículo `ARCHIVED`             | 409   | 200 (registro original intacto) |
| MEMBER con lectura efectiva                  | 403   | 403                             |
| Sin visibilidad, inexistente o inconsistente | 404   | 404                             |

GET sobre un vehículo archivado devuelve 404. Las respuestas 404 son idénticas para inexistente,
sin visibilidad e inconsistente.

## 5. Paginación del listado

- Orden total `vehicle.createdAt ASC, vehicle._id ASC`; `limit` 1..100 (por defecto 20); filtro
  opcional `role`.
- Cursor keyset opaco, versionado (`v: 1`), en base64url canónico, de 256 caracteres como máximo y
  con la posición (`createdAt`, `_id`), el filtro de rol y un binding derivado del usuario
  (SHA-256 truncado). Un cursor malformado, de otra versión, de otro usuario o de otro filtro se
  rechaza con 400. El cursor solo indica posición: nunca concede acceso.
- Cada página reevalúa la autorización. El servidor recorre lotes acotados mediante una agregación
  desde `memberships` con `$lookup` por `_id` a `vehicles`. La agregación aplica un prefiltro de
  lectura que nunca es más estricto que la decisión final (rol coherente con
  `Vehicle.ownerUserId`, permiso directo `vehicle:read`/`vehicle:manage` o un grant `VEHICLE`
  `ONLINE`/`ANY` vigente de la membresía); la decisión final sigue en
  `decideMembershipPermission` + `activeAccessGrantCriteria`. La propiedad canónica y los grants de
  cada lote se resuelven con una consulta `$in` por lote (sin N+1). `nextCursor` se emite desde el
  último resultado autorizado entregado y es `null` al final.
- Tamaño de lote: `limit + 1`; solo si un lote contiene descartes posteriores al escaneo
  (propiedad corrupta o cambios concurrentes) se duplica, hasta `MAX_VEHICLE_SCAN_BATCH` (401).
- No hay snapshot entre páginas: los vehículos creados, archivados, revocados o con permisos
  modificados entre peticiones se reflejan en las páginas siguientes según su posición.

### 5.1. Índices utilizados (sin índices nuevos)

| Consulta                                  | Índice existente                                                               |
| ----------------------------------------- | ------------------------------------------------------------------------------ |
| Membresías activas del usuario (`$match`) | `membership_user_status_vehicle_idx`                                           |
| `$lookup` a `vehicles`                    | `_id_`                                                                         |
| Membresías OWNER del lote                 | `membership_vehicle_status_role_idx` / `membership_active_vehicle_user_unique` |
| Prefiltro de grants (`$lookup`)           | `access_grant_membership_status_idx`                                           |
| Grants del lote                           | `access_grant_lookup_idx` / `access_grant_membership_status_idx`               |

### 5.2. Complejidad

Sea `M` el número de membresías activas del usuario y `k` el tamaño del lote.

- Servidor MongoDB, por lote: recorrido indexado de `M` membresías, `M` búsquedas por `_id` en
  `vehicles` y hasta `M` sondas de grant limitadas a un documento; el `$sort` + `$limit` es un
  top-k que mantiene como máximo `k` documentos en memoria.
- Aplicación, por lote: como máximo `k` candidatos en memoria, una consulta de propietarios y como
  máximo una consulta de grants por permiso de lectura. No se materializan en la aplicación
  conjuntos de membresías ni de `vehicleId` sin límite.
- Lotes por página: uno en ausencia de descartes posteriores al escaneo; con descartes, el
  crecimiento geométrico acota el número de lotes a `O(log(d / k) + d / 401)` para `d` descartes.
- Recorrer todas las páginas cuesta `O(M · M / limit)` en el servidor, porque la clave de orden
  vive en `vehicles` y el keyset solo puede aplicarse tras el `$lookup`. Eliminar ese factor exige
  desnormalizar `createdAt` del vehículo en `Membership` con un índice nuevo y una migración, lo
  que requiere aprobación.

## 6. Semántica de PATCH y DELETE

### 6.1. PATCH

- Campo omitido: se conserva. `null`: limpia el campo (excepto `name`, que no admite `null`).
- `{}` se rechaza; el `userId` interno no cuenta como campo.
- Se ejecuta en `runInVehicleTransaction` tras `lockVerifiedActiveVehicle`, con predicado
  `{ _id, ownerUserId: actor, status: 'ACTIVE' }`, `runValidators` y `updatedByUserId`.

### 6.2. DELETE (archivado lógico)

- Cuerpo opcional; `reason` opcional (máximo 256, sin caracteres de control, recortado).
- En una sola transacción: `status: 'ARCHIVED'`, `archivedAt`, `archivedByUserId`, `archiveReason`;
  las invitaciones `PENDING` vencidas pasan a `EXPIRED` y el resto a `REVOKED`; los grants `ACTIVE`
  vencidos pasan a `EXPIRED` y el resto a `REVOKED`. Las membresías y el historial se conservan.
- Repetir el DELETE devuelve el registro original (`archivedAt`, `archivedByUserId` y
  `archiveReason` no se sobrescriben) tras verificar la propiedad canónica y la `Membership OWNER`.
- No hay mutaciones auxiliares antes de autorizar: un rechazo no modifica ningún documento.

## 7. Concurrencia

- PATCH ‖ DELETE y DELETE ‖ DELETE se serializan mediante el write-lock transaccional sobre el
  vehículo (WriteConflict y reintento de `withTransaction`). Tras un abort por cambio de estado, la
  relación se reclasifica: un PATCH posterior al archivado responde 409 y un DELETE concurrente
  responde con el archivado ganador.
- Las lecturas del listado no se ejecutan en una transacción snapshot; ante estados intermedios
  fallan cerrado (el vehículo se omite).

## 8. Device Service y BLE

TKT-011 no modifica Device Service. Archivar un vehículo bloquea las nuevas autorizaciones y
vinculaciones que Vehicle evalúa (por ejemplo `canLinkDeviceToVehicle`), pero no elimina registros
de `device_db`, no revoca credenciales BLE ya emitidas y no desactiva físicamente ningún ESP32. La
revocación distribuida hacia dispositivos queda pendiente para un ticket posterior.

## 9. Correcciones transversales

- Validación del Gateway: el JSON Schema que valida Ajv conserva tipos, `minLength: 1` y
  `additionalProperties: false`, pero no aplica el `maxLength` generado sobre el valor crudo de los
  campos de texto del vehículo; el contrato Zod compartido con Vehicle aplica el límite tras el
  `trim`. Gateway y Vehicle aceptan y rechazan los mismos valores rodeados de espacios.
- `inviteMember`: la expiración durable de invitaciones vencidas solo se persiste después de una
  autorización de solo lectura (propietario canónico o MEMBER con `vehicle:manage` o
  `invitation:create`). La transacción repite la comprobación bajo bloqueo.

## 10. Limitaciones conocidas

- Sin snapshot entre páginas (sección 5).
- Coste cuadrático del recorrido completo en `M` (sección 5.2).
