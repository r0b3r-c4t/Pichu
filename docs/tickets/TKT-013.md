# TKT-013 — Autorización por recurso

## 1. Propósito y alcance

TKT-013 consolida en un único núcleo la autorización que Vehicle Service ya aplicaba de forma
dispersa (resolución del sujeto, permisos base, `AccessGrant`, propiedad canónica y bindings de
recursos externos) y lo extiende a los recursos `DEVICE` y `MODULE` con coherencia
permiso/recurso.

Vehicle sigue siendo la autoridad de autorización; no se crea ningún microservicio. No se
añaden endpoints, colecciones, índices, migraciones ni dependencias. No se modifican Gateway,
Identity, Device, Automation, contratos compartidos, firmware ni frontend.

Fuera de alcance: la fuente autoritativa de bindings `DEVICE`/`MODULE` (Device/Automation), la
política offline definitiva, la separación modo ONLINE/OFFLINE frente a transporte BLE/WIFI, la
emisión de credenciales de control y cualquier operación de actuadores.

## 2. Estructura

| Archivo                                          | Responsabilidad                                                                     |
| ------------------------------------------------ | ----------------------------------------------------------------------------------- |
| `src/services/resource-authorization.service.ts` | Núcleo: contexto, evidencia, sujeto, decisión, grants, persistencia, reloj, errores |
| `src/services/vehicle-errors.ts`                 | `VehicleServiceError` y auditoría, extraídos para evitar una importación circular   |
| `src/models/vehicle-constants.ts`                | Catálogo de evaluación por recurso (`EVALUABLE_PERMISSIONS_BY_RESOURCE`)            |
| `src/services/vehicle.service.ts`                | Adaptadores compatibles y políticas de operación; reexporta errores y tipos         |
| `src/app.ts`                                     | `deviceLink`: `DATABASE_UNAVAILABLE` → 503 antes de contactar con Device            |

Dependencias: `vehicle.service.ts` → `resource-authorization.service.ts` → `vehicle-errors.ts`,
modelos y constantes. El núcleo no importa `vehicle.service.ts`.

### 2.1. Canal de evaluación

`evaluate(contexto)`:

1. Validación del contexto en tiempo de ejecución: identificadores `ObjectId`, canal, tipo de
   recurso, permiso conocido y no comodín, permiso aplicable al recurso.
2. Verificación de la evidencia de propiedad para `DEVICE`/`MODULE` (sin E/S).
3. Resolución del sujeto (vehículo, membresía `OWNER` canónica y membresía del actor).
4. Decisión por rol, permisos reservados y permisos base.
5. Búsqueda de un `AccessGrant` efectivo solo si la decisión lo requiere.

Denegación por defecto: cualquier caso no previsto produce `allowed: false`.

### 2.2. Interfaz

| Método                     | Semántica                                                                       |
| -------------------------- | ------------------------------------------------------------------------------- |
| `evaluate`                 | Decisión completa con `reason`, `category`/`source`, `membershipId`, `grantId`  |
| `evaluateAnyOf`            | Permitido si alguno lo está; una resolución del sujeto y una consulta de grants |
| `hasPermission`            | `evaluate(...).allowed`                                                         |
| `assertPermission`         | Devuelve la decisión ALLOW o lanza (§6); audita la denegación                   |
| `resolveSubject`           | Sujeto con rol `OWNER`/`MEMBER` o motivo de denegación                          |
| `isOwner`                  | `hasRole(..., 'OWNER')`                                                         |
| `isMember`                 | Membresía `ACTIVE` coherente de cualquier rol: **incluye al `OWNER`**           |
| `hasRole`                  | Coincidencia exacta de rol; un rol inválido nunca coincide                      |
| `hasVehicleReadAccess`     | Lectura TKT-011: `vehicle:read` o `vehicle:manage`                              |
| `filterReadableCandidates` | Lectura por lotes con las mismas reglas, sin N+1                                |

Opciones: `session` (§5), `clock` (reloj del servidor inyectable; una sola captura por
evaluación) y `audit`. El actor procede siempre del contexto autenticado; el contexto no admite
roles, permisos, fechas, membresías ni bindings declarados por el cliente.

### 2.3. Adaptadores

| Adaptador                         | Delegación                                                                  |
| --------------------------------- | --------------------------------------------------------------------------- |
| `evaluateVehiclePermission`       | `evaluate`; conserva la forma de resultado anterior y `now` como reloj fijo |
| `canAccessVehicle(v, u)`          | Sin permiso: `hasVehicleReadAccess` (incluye `vehicle:manage`)              |
| `canAccessVehicle(v, u, p)`       | `hasPermission` sobre `VEHICLE`                                             |
| `canLinkDeviceToVehicle`          | `evaluateAnyOf(['vehicle:manage', 'device:link'])` sobre `VEHICLE`, ONLINE  |
| `filterReadableVehicleCandidates` | `filterReadableCandidates`                                                  |
| Prefiltro de listados             | Usa `activeAccessGrantCriteria` del núcleo para el `$match` de grants       |
| Emisión de invitaciones           | `resolveSubject` del núcleo; la autoridad sigue siendo solo base            |

Los listados conservan la paginación keyset acotada con reautorización por página y el mismo
número de consultas por página (TKT-011).

## 3. Matriz permiso/recurso

| Recurso   | Permisos evaluables                                                                                            |
| --------- | -------------------------------------------------------------------------------------------------------------- |
| `VEHICLE` | Reservados del `OWNER`, `vehicle:read`, `vehicle:update`, `vehicle:manage`, `invitation:create`, `device:link` |
| `DEVICE`  | `device:read`, `device:connect`, `device:command`                                                              |
| `MODULE`  | `module:read`, `module:configure`, `module:actuate`                                                            |

- Una combinación incompatible se rechaza con `PERMISSION_RESOURCE_MISMATCH` (categoría
  `INVALID_CONTEXT`) también para el `OWNER`.
- El catálogo de evaluación es independiente del catálogo de concesión de grants, que no se amplía.
- Los permisos reservados siguen siendo exclusivos del `OWNER`.

### 3.1. Incompatibilidades documentadas

- `device:read` deja de evaluarse sobre `VEHICLE`: un `MEMBER` con `device:read` base lo ejerce
  sobre un `DEVICE` concreto con evidencia verificada.
- Un `AccessGrant` `VEHICLE` con `device:read` ya no puede crearse (§4.2). Los registros
  históricos con esa combinación se conservan, siguen siendo válidos para el modelo y gestionables,
  pero nunca conceden acceso: no se evalúan sobre `VEHICLE` ni se extienden a `DEVICE`.

## 4. Semántica de permisos base y grants

| Sujeto / caso                         | ONLINE                            | BLE_OFFLINE                       |
| ------------------------------------- | --------------------------------- | --------------------------------- |
| `OWNER` canónico, permiso compatible  | ALLOW (`OWNER_ROLE`)              | DENY `BLE_OWNER_GRANT_REQUIRED`   |
| `MEMBER`, permiso reservado           | DENY `OWNER_PERMISSION_FORBIDDEN` | DENY `OWNER_PERMISSION_FORBIDDEN` |
| `MEMBER`, permiso base compatible     | ALLOW (`MEMBERSHIP_PERMISSION`)   | Requiere grant                    |
| `MEMBER`, permiso concedible sin base | Requiere grant                    | Requiere grant                    |
| `MEMBER`, permiso no concedible       | DENY `PERMISSION_NOT_GRANTED`     | DENY `PERMISSION_NOT_GRANTED`     |

- Los permisos base de un `MEMBER` se aplican en ONLINE a los recursos compatibles sin grant
  adicional; `DEVICE`/`MODULE` exigen evidencia verificada. Nunca autorizan BLE_OFFLINE.
- Un ALLOW genérico no sustituye las políticas de operación: actualizar o archivar el vehículo
  sigue siendo exclusivo del `OWNER`, la administración de membresías también y la autoridad de
  invitación sigue siendo exclusivamente base (`vehicle:manage` o `invitation:create`).
- La denegación BLE_OFFLINE del `OWNER` es provisional y **no** es la política offline definitiva.

### 4.1. `AccessGrant` efectivo

Coincidencia exacta de: `vehicleId`, `subjectUserId`, `membershipId` de la membresía actual,
`scopeType` y `scopeResourceId` del recurso, permiso, canal (`channel` exacto o `ANY`), estado
`ACTIVE` sin revocación, `startsAt <= now` (inclusivo) y `expiresAt > now` (exclusivo).

- Un grant sin `expiresAt` solo cuenta en ONLINE; BLE_OFFLINE/ANY sin caducidad nunca cuentan,
  también en documentos históricos.
- Un grant `VEHICLE` no se extiende a `DEVICE`/`MODULE`; un grant `DEVICE` autoriza solo ese
  dispositivo.
- Los grants no confieren autoridad de invitación. No existe CRUD público de grants.
- Se mantienen las cascadas de TKT-012 (suspensión, revocación, abandono, archivado).
- `createAccessGrant` exige ahora evidencia verificada para `DEVICE`/`MODULE` coherente en tipo,
  `resourceId` y `vehicleId`; sin ella responde `VALIDATION_ERROR` sin persistir nada. El historial
  no se migra ni se inventan bindings para grants anteriores.
- Registros inconsistentes en persistencia (BLE_OFFLINE/ANY con `expiresAt` nulo, ausente o de
  tipo no fecha) nunca conceden acceso: el criterio exige `expiresAt > now` de tipo fecha salvo
  ONLINE sin caducidad. Las cascadas los revocan igualmente.

### 4.2. Catálogos de creación y de almacenamiento

| Catálogo       | Función                           | Uso                                                                                                       |
| -------------- | --------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Almacenamiento | `isAccessGrantPermissionForScope` | Validación del modelo: lectura, auditoría, expiración y revocación de registros, incluidos los históricos |
| Creación       | `isIssuableAccessGrantPermission` | `createAccessGrant` y elegibilidad de grant en la decisión                                                |

- Creación = almacenable para el ámbito **y** evaluable sobre el mismo tipo de recurso. La única
  combinación almacenable pero no creable es `VEHICLE` + `device:read`; se rechaza con
  `VALIDATION_ERROR` antes de cualquier escritura o transacción.
- No se amplía ningún permiso concedible ni se modifican contratos compartidos. No hay migración:
  los registros históricos se conservan y pueden revocarse, expirar o revocarse en cascada.
- No existe una lectura administrativa pública de grants; su lectura interna (modelo) no cambia.

## 5. Evidencia de propiedad de recursos externos

- `createVerifiedExternalResourceBinding` construye la evidencia interna: objeto congelado con
  copias congeladas de los `ObjectId`, registrado en un `WeakMap` privado del módulo junto con los
  hechos capturados en la emisión (identificadores en hexadecimal). Copias, objetos con la misma
  forma o JSON deserializado no son evidencia.
- `verifyExternalResourceBinding` compara solo los hechos capturados (registro, `isActive`, tipo,
  `resourceId` y `vehicleId`): mutar después los `ObjectId` del llamante, o intentar mutar los
  expuestos, no cambia la evidencia efectiva.
- No existe todavía una fuente autoritativa: ningún módulo de producción fabrica evidencia. Una
  prueba estática verifica que el identificador solo aparece en su definición y en el re-export
  de `vehicle.service.ts` para fixtures de prueba. Por tanto `DEVICE`/`MODULE` fallan cerrado en producción
  (`UNVERIFIED_EXTERNAL_RESOURCE`); las pruebas usan fixtures explícitos.
- Vehicle no accede a las bases de Device ni Automation y no se añaden endpoints.

## 6. Errores

| Situación                              | Decisión / error                                                | HTTP |
| -------------------------------------- | --------------------------------------------------------------- | ---- |
| Contexto inválido (código de servidor) | DENY categoría `INVALID_CONTEXT`; `assert` → `VALIDATION_ERROR` | 400  |
| Denegación con vehículo visible        | DENY `DENIED`; `assert` → `FORBIDDEN`                           | 403  |
| Denegación sin visibilidad             | DENY `DENIED`; `assert` → `NOT_FOUND`                           | 404  |
| Propiedad inconsistente                | DENY `INCONSISTENT_STATE` auditado; respuesta uniforme          | 404  |
| Base de datos no disponible            | `DATABASE_UNAVAILABLE` (nunca ALLOW)                            | 503  |
| Error de programación                  | Se propaga sin convertirse en 503                               | 500  |

- `DATABASE_UNAVAILABLE`: conexión Mongoose no lista, o errores de conectividad del driver
  (red, selección de servidor, conexión cerrada) en lecturas sin sesión. Con sesión, los errores
  se propagan intactos para conservar las etiquetas de reintento de la transacción.
- `runInVehicleTransaction` aplica el mismo clasificador (`isDatabaseUnavailableError`) al error
  que escapa de `withTransaction`, es decir, después de que el driver haya agotado sus reintentos
  (`TransientTransactionError`, `UnknownTransactionCommitResult`), y al fallo de `startSession`.
  Errores de dominio, validación, WriteConflict persistente, duplicados (E11000) y errores de
  programación se propagan sin cambios. Todas las mutaciones transaccionales responden así 503
  ante caídas confirmadas, sin exponer el detalle del driver.
- `deviceLink` responde 503 sin contactar con Device cuando la autorización no puede evaluarse;
  las denegaciones siguen siendo 404 uniforme. Las razones de denegación no se exponen.

## 7. Concurrencia

- `session` opcional propagada a todas las consultas de una evaluación, siempre en secuencia
  (nunca operaciones paralelas sobre la misma sesión).
- Una lectura con sesión ve la instantánea de la transacción (incluidos sus cambios no
  confirmados) pero **no es una barrera de escritura**: una suspensión confirmada después de la
  instantánea no cambia la respuesta de la evaluación. Solo la escritura condicional sobre el
  documento de autoridad detecta el conflicto (WriteConflict).
- Las mutaciones conservan sus bloqueos (`lockVerifiedActiveVehicle(WithOwner)`) y escrituras
  condicionales, y revalidan la autoridad dentro de la transacción; la evaluación previa es solo
  un filtro temprano.
- Sin caché positiva y sin llamadas remotas dentro de transacciones.

Pruebas reales sobre replica set: evaluación con sesión (membresía, grant y archivado no
confirmados), instantánea frente a suspensión concurrente, e invitación delegada frente a
cambio de permisos, suspensión y revocación (barrera determinista y carreras).

La lectura individual (`hasVehicleReadAccess`) reutiliza `filterReadableCandidates` con un único
candidato, por lo que ambos caminos aplican las mismas reglas; una prueba real compara ambos
resultados antes y después de suspensiones y cambios de permisos, con como máximo una consulta de
grants por lote.

## 8. Arquitectura móvil (contexto)

- El teléfono actúa como puente entre el backend y el ESP32 por BLE o Wi-Fi local; el ESP32 no
  tiene Internet.
- El teléfono no es la autoridad final: la autenticidad de las órdenes y la seguridad física deben
  verificarse en el ESP32. Esos protocolos no se implementan aquí.
- Se mantienen los canales `ONLINE`, `BLE_OFFLINE` y `ANY`. La separación entre modo
  (ONLINE/OFFLINE) y transporte (BLE/WIFI) queda para tickets futuros. Los contratos BLE no se
  modifican.

## 9. Hallazgos de Device pendientes (no resueltos por TKT-013)

- La lectura de dispositivos en Device se basa en `linkedByUserId`.
- Un miembro revocado puede conservar la lectura de dispositivos que vinculó.
- El `OWNER` puede no acceder a un dispositivo vinculado por otro miembro.
- TOCTOU entre la autorización del vínculo en Vehicle y la finalización del desafío en Device.
- Las rutas de revocación de dispositivos están deshabilitadas.
- No existe una fuente de bindings `DEVICE`/`MODULE` consumible por Vehicle.

`linkedByUserId` es información histórica de auditoría, no propiedad. Estos hallazgos deben
resolverse antes de habilitar operaciones físicas o credenciales de control.

## 10. Decisiones pendientes y riesgos

- Fuente autoritativa de evidencia `DEVICE`/`MODULE` y su contrato con Device/Automation.
- Política offline definitiva del `OWNER` y separación modo/transporte.
- Las escrituras y lecturas fuera de transacción que no pasan por el núcleo (por ejemplo, la
  persistencia previa de invitaciones vencidas, `revokeAccessGrant`, `expireElapsedAccessGrants`
  y la agregación de listados) siguen devolviendo 500 ante errores de conectividad del driver.
  Unificarlo exige un manejador transversal y queda fuera de este ticket.
- Ante una caída durante una transacción, `withTransaction` reintenta hasta su límite interno
  antes de que se responda 503.
- Retirar físicamente `device:read` del catálogo de almacenamiento `VEHICLE` requeriría migrar
  o invalidar registros históricos; no se hace.
