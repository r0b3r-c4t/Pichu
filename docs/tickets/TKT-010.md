# TKT-010 — Vehicle Foundation (Multi-Vehicle & Multi-Brand)

## 1. Propósito y alcance

`TKT-010` establece la base fundacional de dominio, persistencia, integridad transaccional, readiness e invariantes de autorización de **`@pichu/vehicle-service`** sobre su base lógica exclusiva `vehicle_db`.

Aunque la primera unidad de validación física del proyecto es un **Mazda 3 2.0 sedán automático 2011**, el dominio de `Vehicle Service` es **agnóstico al fabricante, modelo, año, carrocería, motorización y hardware instalado**:

- Un usuario puede ser propietario (`OWNER`) de múltiples vehículos simultáneamente.
- Un usuario puede ser miembro (`MEMBER`) de múltiples vehículos de distintos propietarios.
- Un vehículo puede tener múltiples miembros con permisos delegados acotados.
- Un vehículo puede vincular múltiples dispositivos físicos (por ejemplo, varios nodos ESP32 por vehículo) a través de `Device Service`.
- Los metadatos técnicos descriptivos son opcionales y nunca asumen valores por defecto de Mazda ni enumeraciones cerradas de un único fabricante.
- Todos los permisos, membresías, invitaciones y concesiones (`AccessGrant`) están estrictamente aislados por `vehicleId`.

Este ticket **no** modifica contratos públicos aprobados en `@pichu/contracts`, **no** introduce control físico de actuadores y **no** emite credenciales criptográficas BLE offline.

## 2. Los cuatro modelos de dominio (`vehicle_db`)

Todos los modelos utilizan `strict: 'throw'`, `timestamps: true` (`createdAt`, `updatedAt`) y validadores explícitos tanto a nivel de esquema como en la capa de servicio transaccional (`vehicle.service.ts`). `connectDatabase` mantiene `autoIndex: false` para impedir mutaciones implícitas de índices en producción.

## 3. Índices declarados e invariantes físicas en MongoDB

### 3.1. `vehicles`

- `vehicle_owner_status_created_idx`: `{ ownerUserId: 1, status: 1, createdAt: 1, _id: 1 }` (**no único**, permite múltiples vehículos por propietario).
- `vehicle_status_id_idx`: `{ status: 1, _id: 1 }`.

### 3.2. `memberships`

- `membership_active_vehicle_user_unique`: `{ vehicleId: 1, userId: 1 }`, `unique: true`, `partialFilterExpression: { revokedAt: null }`.
  - Impide duplicar membresías `ACTIVE` o `SUSPENDED` para el mismo `(vehicleId, userId)` y **permite emitir nuevas membresías tras una revocación** sin borrar el historial `REVOKED`.
- `membership_single_active_owner_unique`: `{ vehicleId: 1 }`, `unique: true`, `partialFilterExpression: { role: 'OWNER', status: 'ACTIVE' }`.
  - Garantiza a nivel de motor MongoDB que nunca existan dos `OWNER` activos para el mismo vehículo.
- `membership_user_status_vehicle_idx`: `{ userId: 1, status: 1, vehicleId: 1 }` (**no único**, permite a un usuario pertenecer a múltiples vehículos).
- `membership_vehicle_status_role_idx`: `{ vehicleId: 1, status: 1, role: 1 }`.

### 3.3. `invitations`

- `invitation_pending_vehicle_invitee_unique`: `{ vehicleId: 1, inviteeUserId: 1 }`, `unique: true`, `partialFilterExpression: { status: 'PENDING' }`.
  - Impide duplicados `PENDING` concurrentes conservando ilimitadas invitaciones históricas en `ACCEPTED`, `REVOKED` o `EXPIRED`.
- `invitation_invitee_status_expires_idx`: `{ inviteeUserId: 1, status: 1, expiresAt: 1 }`.
- `invitation_vehicle_status_expires_idx`: `{ vehicleId: 1, status: 1, expiresAt: 1 }`.
- **Prohibición explícita:** No existe ningún índice TTL (`expireAfterSeconds`) sobre `expiresAt`.

### 3.4. `access_grants`

- `access_grant_lookup_idx`: `{ vehicleId: 1, subjectUserId: 1, status: 1, scopeType: 1, scopeResourceId: 1, expiresAt: 1 }` (**no único**: soporta múltiples grants independientes por recurso, canal y ventana temporal).
- `access_grant_membership_status_idx`: `{ membershipId: 1, status: 1 }` (soporta cascada transaccional eficiente al revocar una `Membership`).
- `access_grant_vehicle_status_expires_idx`: `{ vehicleId: 1, status: 1, expiresAt: 1 }` (barrido de expiración y cascada al archivar vehículo).

## 4. Estados e invariantes de transición

Las transiciones se validan explícitamente en `vehicle-constants.ts` y mediante predicados atómicos (`findOneAndUpdate` / `updateMany` con condiciones sobre el estado previo) y `runValidators: true`, sin depender exclusivamente de hooks `pre('validate')`.

| Entidad                 | Estado inicial | Transiciones válidas                                                                  | Estados terminales               |
| ----------------------- | -------------- | ------------------------------------------------------------------------------------- | -------------------------------- |
| `Vehicle`               | `ACTIVE`       | `ACTIVE → ARCHIVED`                                                                   | `ARCHIVED`                       |
| `Membership` (`OWNER`)  | `ACTIVE`       | Ninguna en TKT-010 (inmutablemente `ACTIVE`)                                          | —                                |
| `Membership` (`MEMBER`) | `ACTIVE`       | `ACTIVE → SUSPENDED`, `SUSPENDED → ACTIVE`, `ACTIVE → REVOKED`, `SUSPENDED → REVOKED` | `REVOKED`                        |
| `Invitation`            | `PENDING`      | `PENDING → ACCEPTED`, `PENDING → REVOKED`, `PENDING → EXPIRED`                        | `ACCEPTED`, `REVOKED`, `EXPIRED` |
| `AccessGrant`           | `ACTIVE`       | `ACTIVE → REVOKED`, `ACTIVE → EXPIRED`                                                | `REVOKED`, `EXPIRED`             |

### Cascadas transaccionales

1. **`createVehicle`:** Crea `Vehicle` (`ownerUserId = actor`) + `Membership` (`role: 'OWNER'`, `status: 'ACTIVE'`) en una sola transacción `snapshot` / `w: 'majority'`. Si falla cualquiera de los dos pasos, no queda ningún documento huérfano.
2. **`acceptInvitation`:**
   - Si la invitación ya venció (`expiresAt <= now`), persiste `status: 'EXPIRED'` **fuera** de la transacción abortable para que el cambio de estado nunca se pierda por rollback al devolver rechazo/no encontrado.
   - Si está vigente, reclama atómicamente la invitación `PENDING` (`status: 'PENDING' → 'ACCEPTED'`) y crea la `Membership` `MEMBER` dentro de una única transacción. Ante llamadas concurrentes, exactamente una gana.
3. **`revokeMembership`:** Marca la `Membership` `MEMBER` como `REVOKED` y revoca en la misma transacción todos sus `AccessGrant` `ACTIVE` asociados por `membershipId`.
4. **`archiveVehicle`:** Marca el `Vehicle` como `ARCHIVED` y revoca en la misma transacción todas las `Invitation` `PENDING` y todos los `AccessGrant` `ACTIVE` del vehículo. Un vehículo `ARCHIVED` deniega lectura operativa, invitaciones, vinculación de dispositivos y emisión de nuevos permisos.
5. **Barreras de escritura contra _write skew_ (`lockVerifiedActiveVehicle` y lock sobre `Membership`):** En MongoDB `snapshot` isolation, una simple lectura (`findOne`) sobre el documento padre no impide modificaciones concurrentes en documentos hijos distintos. Por ello, `inviteMember`, `acceptInvitation`, `revokeMembership` y `createAccessGrant` adquieren barreras condicionales de escritura (`findOneAndUpdate`) sobre el `Vehicle` `ACTIVE` (y sobre la `Membership` `ACTIVE` en `createAccessGrant`) dentro de `session.withTransaction`, forzando serialización determinista por `WriteConflict` frente a `archiveVehicle` y `revokeMembership`.

## 5. Ownership canónico y protección del propietario

1. **`Vehicle.ownerUserId` es la fuente canónica de propiedad.**
2. **`Membership` `OWNER` es su representación sincronizada transaccionalmente.**
3. `loadVerifiedActiveVehicle` comprueba en cada operación sensible y consulta de autorización que:
   - El `Vehicle` exista y tenga `status === 'ACTIVE'`.
   - Exista **exactamente una** `Membership` no revocada con `role: 'OWNER'` y `status === 'ACTIVE'`.
   - `ownerMembership.userId.equals(vehicle.ownerUserId)` sea verdadero.
4. **Fail-closed ante inconsistencia:** Si por manipulación manual o corrupción de datos existe discrepancia entre `Vehicle.ownerUserId` y `Membership` `OWNER`, `Vehicle Service` **deniega el acceso** a ambas partes y registra un evento de auditoría (`canonical_owner_mismatch`).
5. **Protecciones activas:**
   - Prohibido suspender, revocar o degradar la `Membership` `OWNER`.
   - Prohibidas las auto-invitaciones (`inviterUserId === inviteeUserId`).
   - Prohibido invitar al `ownerUserId` como `MEMBER`.
   - Prohibido escalar a `OWNER` mediante `Invitation` (`targetRole` fijo en `'MEMBER'`) o `AccessGrant`.

## 6. Catálogo y precedencia de permisos

### 6.1. Catálogo cerrado de permisos conocidos

Se rechaza cualquier wildcard (`*`, `vehicle:*`, etc.) y cualquier identificador desconocido:

- **Reservados al `OWNER` (`OWNER_RESERVED_PERMISSIONS`):** `vehicle:owner`, `vehicle:delete`, `vehicle:archive`, `vehicle:transfer-ownership`, `membership:manage`, `access-grant:manage`.
- **Delegables a `Membership` (`MEMBER`) en ámbito `VEHICLE` (`ONLINE`):** `vehicle:read`, `vehicle:update`, `vehicle:manage`, `invitation:create`, `device:read`, `device:link` (además de los permisos de dispositivo/módulo cuando se evalúan junto con `AccessGrant`).
- **Delegables en `AccessGrant` por `scopeType`:**
  - `VEHICLE`: `vehicle:read`, `vehicle:update`, `device:read`, `device:link`.
  - `DEVICE`: `device:read`, `device:connect`, `device:command`.
  - `MODULE`: `module:read`, `module:configure`, `module:actuate`.

### 6.2. Orden estricto de evaluación (`evaluateVehiclePermission`)

1. **Validación sintáctica y de catálogo:** Si el permiso no pertenece a `ALL_KNOWN_PERMISSIONS` o contiene wildcards/caracteres de control → **DENY** (`UNKNOWN_OR_INVALID_PERMISSION`).
2. **Coherencia de ámbito (`scopeType` / `scopeResourceId`):**
   - `VEHICLE` exige `scopeResourceId === null`.
   - `DEVICE` y `MODULE` exigen `scopeResourceId !== null` y un `verifiedResourceBinding` activo emitido por el servicio propietario (`Device Service` o `Automation Service`) cuyo `vehicleId` coincida exactamente con el vehículo evaluado → si falta o no coincide, **DENY** (`UNVERIFIED_EXTERNAL_RESOURCE`).
3. **Estado e integridad del vehículo:** Si el vehículo no existe, está `ARCHIVED` o presenta inconsistencia `ownerUserId ↔ Membership OWNER` → **DENY** (`VEHICLE_UNAVAILABLE_OR_INCONSISTENT`).
4. **Membresía activa del sujeto:** Se exige una `Membership` con `vehicleId`, `userId`, `status === 'ACTIVE'`, `suspendedAt === null` y `revokedAt === null`. Si está `SUSPENDED`, `REVOKED` o no existe → **DENY** (`MEMBERSHIP_INACTIVE_OR_MISSING`). _Ningún `AccessGrant` puede reactivar ni puentear una membresía suspendida o revocada._
5. **Autorización de `OWNER`:**
   - En canal `ONLINE`, el `OWNER` canónico verificado recibe acceso (`source: 'OWNER_ROLE'`).
   - En canal `BLE_OFFLINE`, incluso para el propietario se requiere credencial/grant explícito con expiración (`BLE_OWNER_GRANT_REQUIRED`), preparando la futura emisión criptográfica acotada.
6. **Bloqueo de permisos reservados en `MEMBER`:** Si `membership.role === 'MEMBER'` y el permiso está en `OWNER_RESERVED_PERMISSIONS` → **DENY** (`OWNER_PERMISSION_FORBIDDEN`).
7. **Permisos base de `Membership` (`ONLINE` + `VEHICLE`):** Si `scopeType === 'VEHICLE'`, `channel === 'ONLINE'` y `membership.permissions` incluye el permiso → **ALLOW** (`source: 'MEMBERSHIP_PERMISSION'`).
8. **Concesiones granulares (`AccessGrant`):** Se busca al menos un `AccessGrant` con:
   - Mismo `vehicleId`, `membershipId: membership._id` (garantiza **no herencia** tras revocación y nueva membresía) y `subjectUserId: userId`.
   - Mismo `scopeType` y `scopeResourceId`.
   - Canal compatible (`ONLINE` acepta `ONLINE | ANY`; `BLE_OFFLINE` acepta `BLE_OFFLINE | ANY`).
   - `status === 'ACTIVE'`, `revokedAt === null`, `expiredAt === null`.
   - Vigencia temporal estricta: `startsAt <= now` y (`expiresAt === null` o `expiresAt > now`).
   - `permissions` contiene el permiso solicitado.
   - Si existe → **ALLOW** (`source: 'ACCESS_GRANT'`); en caso contrario → **DENY** (`PERMISSION_NOT_GRANTED`).

## 7. Límites de `AccessGrant` y límites de revocación `BLE_OFFLINE`

### 7.1. Límites deliberados de `AccessGrant` en TKT-010

- **Sin delegación por `MEMBER`:** Solo el propietario canónico (`Vehicle.ownerUserId`) puede crear o revocar `AccessGrant` en esta fase.
- **Sin índice único por scope:** Un mismo miembro puede tener múltiples grants independientes (p. ej. un grant `ONLINE` de lectura permanente sobre `deviceA` y un grant temporal de fin de semana `BLE_OFFLINE` con `device:command` sobre el mismo `deviceA`). Revocar uno no afecta a los demás.
- **Vinculación estricta a `membershipId`:** Al revocar una `Membership`, todos sus grants `ACTIVE` se revocan en cascada dentro de la misma transacción. Si el usuario vuelve a ser invitado posteriormente, recibe un nuevo `membershipId` y jamás hereda grants anteriores.
- **Sin motor externo ni emisión de tokens BLE:** `DEVICE` y `MODULE` quedan listos estructuralmente en persistencia y evaluación de dominio, pero `Vehicle Service` nunca asume por sí solo que un `deviceId` o `moduleId` pertenece a un `vehicleId` sin verificación del servicio propietario.

### 7.2. Límites físicos y criptográficos de revocación `BLE_OFFLINE`

Cuando un teléfono interactúa por Bluetooth Low Energy con un ESP32 en un estacionamiento subterráneo o zona sin cobertura celular, ni el teléfono ni el ESP32 pueden consultar MongoDB en tiempo real:

1. **Ventana de exposición acotada obligatoria:** Por diseño, todo grant con canal `BLE_OFFLINE` o `ANY` exige `expiresAt` explícito no nulo. No existen permisos offline perpetuos.
2. **Revocación inmediata en plano online vs convergencia diferida en plano offline:** Revocar una `Membership` o un `AccessGrant` en `vehicle_db` bloquea instantáneamente cualquier operación `ONLINE` y cualquier renovación futura de credenciales, pero un token/credencial offline previamente aprovisionado (en el futuro ticket de protocolo BLE) podría seguir siendo presentado ante el ESP32 hasta que:
   - Expire su ventana corta (`expiresAt`), o
   - El ESP32 o la app sincronicen una nueva época de revocación / lista de revocación firmada al recuperar conectividad.
3. **Separación respecto de seguridad física:** La autorización BLE nunca sustituye las salvaguardas físicas de hardware/firmware del vehículo (estado seguro en arranque/reset, watchdog, pérdida de latido y preservación de protecciones OEM).

## 8. Arquitectura Multi-Vehicle, Multi-Brand y evolución hacia `VehicleProfile`

### 8.1. Modelo de 4 capas desacopladas

Para soportar cualquier fabricante y modelo sin acoplar `Vehicle Service` a detalles electrónicos de un vehículo particular, PICHU separa estrictamente cuatro conceptos:

1. **Compatibilidad (`VehicleProfile` — futuro):** Qué capacidades o señales soporta teóricamente una plataforma/generación vehicular (ej. Mazda 3 BL 2010–2013 vs Toyota Corolla Cross XG10 vs Ford Ranger T6).
2. **Hardware instalado (`Device Service`):** Qué nodos físicos ESP32, sensores o arneses están realmente instalados, autenticados criptográficamente y activos (`status: 'ACTIVE'`) en esa unidad `vehicleId`.
3. **Funcionalidad habilitada (`Automation Service`):** Qué módulos lógicos (`MODULE`), reglas y estados reportados están configurados y habilitados operativamente sobre el hardware instalado de ese vehículo.
4. **Autorización (`Vehicle Service`):** Quién es el propietario (`ownerUserId`), qué usuarios tienen `Membership` activa y qué permisos o `AccessGrant` vigentes poseen sobre `vehicleId`, `deviceId` o `moduleId`.

Una operación real sobre un vehículo requiere la intersección válida de las cuatro capas; tener permiso en `Vehicle Service` no implica que el hardware exista ni que el actuador sea seguro de accionar.

### 8.2. Extensiones futuras previstas (no implementadas en TKT-010)

En tickets posteriores, `Vehicle` podrá incorporar opcionalmente:

- `profileId`: referencia opcional a un `VehicleProfile` versionado cuando exista catálogo técnico para esa generación/modelo (manteniendo soporte completo para vehículos genéricos con `profileId = null`).
- Catálogos vehiculares, decodificación opcional de VIN (con tratamiento de dato sensible/PII) y plantillas de módulos compatibles (`supportedCapabilities`) coordinadas con `Automation Service`.

## 9. Migración controlada de datos e índices heredados

`Vehicle Service` **prohíbe** `syncIndexes()` destructivo y el borrado automático de índices en el arranque de producción. Para entornos que contengan datos o índices previos a `TKT-010`, `src/database/migration.ts` proporciona dos operaciones explícitas:

### 9.1. Fase 1 — Preflight de solo lectura (`inspectVehicleMigrationPreflight`)

Inspecciona `vehicle_db` sin modificar documentos ni índices y detecta:

1. Índices TTL destructivos heredados sobre `invitations.expiresAt` (`destructiveInvitationTtlIndexNames`, típicamente `expiresAt_1`).
2. Índices únicos heredados no parciales sobre `memberships` (`{ vehicleId: 1, userId: 1 }` sin `partialFilterExpression`, que impedirían re-membresía tras revocación).
3. Invitaciones `PENDING` cuyo `expiresAt <= now` (`expiredPendingInvitationsCount`).
4. Documentos heredados sin campos estructurales nuevos (`status` en `vehicles`/`memberships`, `targetRole` en `invitations`).
5. **Inconsistencias bloqueantes (`canAutoMigrateSafely === false`):**
   - Vehículos sin `createdByUserId` o membresías sin `grantedByUserId` (**nunca se inventan actores históricos falsos mediante defaults automáticos**; deben atribuirse verificadamente antes de migrar).
   - Vehículos activos sin `Membership` `OWNER` activa única o con discrepancia `Vehicle.ownerUserId !== ownerMembership.userId`.
   - Pares `(vehicleId, inviteeUserId)` con múltiples invitaciones `PENDING` no vencidas.

### 9.2. Fase 2 — Ejecución controlada (`applyControlledVehicleMigration`)

1. Ejecuta `inspectVehicleMigrationPreflight(db)` y aborta con `VehicleMigrationBlockedError` si `canAutoMigrateSafely` es `false`.
2. Elimina primero de forma idempotente cualquier índice TTL destructivo sobre `invitations` para detener de inmediato purgas automáticas en segundo plano.
3. Transiciona invitaciones `PENDING` vencidas a `EXPIRED` (`expiredAt = now`) y completa campo por campo (`{ [field]: { $exists: false } }`) únicamente valores estructurales seguros no atribuibles a actores, sin sobrescribir datos preexistentes.
4. Crea todas las colecciones e índices de reemplazo declarados en `VEHICLE_DOMAIN_MODELS` (incluido `membership_active_vehicle_user_unique`) **antes** de retirar el índice único heredado de `memberships`, garantizando **cero ventanas operativas sin unicidad activa** y recuperación segura ante interrupciones parciales.
5. Ejecuta `dropIndex` idempotente sobre el índice único antiguo no parcial de `memberships` (`vehicleId_1_userId_1`) y valida con `assertCriticalVehicleIndexes(db)`.

### 9.3. Fase 3 — Verificación posterior y Readiness (`assertCriticalVehicleIndexes`)

`/health/ready` ejecuta en cada verificación:

1. `nonces.assertReady()` (`MongoNonceStore`: primario escribible de replica set + índices de nonces).
2. `checkDatabaseConnection()` (`ping: 1` con timeout acotado de `500 ms`).
3. `assertCriticalVehicleIndexes(db)`: devuelve `503 Service Unavailable` si falta cualquiera de los índices críticos de integridad o si aún permanece activo el índice TTL destructivo sobre `invitations.expiresAt`.
